# Архітектура та аудит API

## Джерела

Контракти звірено з актуальним `../residdy_backend/src`: контролерами, DTO, моделями, guard-ами та сервісами. Менеджерський фронтенд `../residdy_managers_crm` використано як джерело технологій, HTTP-транспорту, залежних TypeScript-моделей та стилів. Його `src/shared/new-back*` — довідкові копії, а не джерело нових власних маршрутів.

Перевірено всі контролери, що використовують `PartnerGuard` та `SpecialistGuard`, а також спільні account-auth/account, консультаційні категорії, відгуки і приватні файли. Модулі менеджерських справ, платежів, розсилок, адміністрування й користувацьких підписок не мають власних операцій цих ролей і не включені до кабінету.

## Сесія й розподіл ролей

1. `POST /account-auth/login` повертає `{ token }`.
2. `GET /account/me` підтверджує акаунт і його `type`.
3. Для `PARTNERS` викликається `/partners/me`, для `SPECIALISTS` — `/specialists/me`. Перевіряються ID і відповідність `profile.accountId`.
4. Лише після успішної перевірки токен записується в окремий ключ `residdy_portal_access_token`. `MANAGERS`, `USERS`, невідомі типи та неактивні акаунти відхиляються.
5. Приватна оболонка очікує сесію. Маршрутизатор перевіряє роль до монтування сторінки, у тому числі за прямими URL. Роль не береться з URL, перемикача чи неперевіреного JWT.
6. Ключі даних містять `account.id`; сесія прив’язана до токена. Вихід очищує кеш і токен. Події storage синхронізують вихід між вкладками. Перевірка сесії повторюється при фокусі та кожні п’ять хвилин.
7. `401` від захищеного ресурсного API завершує сесію. `401` від auth-операції може означати неправильний поточний пароль і показується як помилка форми. `403`/`404`/`409`/`410` не маскуються під порожні дані.

Збереження токена у browser storage успадковує підхід менеджерської CRM. Серверний BFF/HttpOnly-cookie refresh-flow не вигадувався: поточний бек повертає bearer-токен без refresh endpoint. Авторитетною перевіркою прав і власника залишається бек. Захист UI не замінює серверні guards.

## Реалізовані маршрути

| Сценарій            | API                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Вхід і сесія        | `POST /account-auth/login`, `GET /account/me`                                                                                                           |
| Активація           | `POST /account-auth/confirm`, `/account-auth/resend`                                                                                                    |
| Відновлення         | `POST /account-auth/forgot-password`, `/account-auth/reset-password`                                                                                    |
| Пароль              | `POST /account-auth/request-password-change`, `/account-auth/change-password`                                                                           |
| Пошта               | `POST /account-auth/request-email-change`, `/account-auth/confirm-email-change`                                                                         |
| Профіль партнера    | `GET/PATCH /partners/me`, `POST /partners/me/avatar`                                                                                                    |
| Компанії            | `GET /partner-companies/my`, `POST /partner-companies`, `GET/PATCH /partner-companies/my/:id`                                                           |
| Опис компанії       | `PATCH /partner-company-info/my/:id`                                                                                                                    |
| Зображення компанії | `POST /partner-companies/my/:id/logo`, `/partner-company-info/my/:id/photo`                                                                             |
| Публікація компанії | `PATCH /partner-companies/my/:id/publish`, `/unpublish`                                                                                                 |
| Банери              | `GET/POST /partner-banners/my`, `GET/PATCH /partner-banners/my/:id`                                                                                     |
| Профіль спеціаліста | `GET/PATCH /specialists/me`, `POST /specialists/me/avatar`, `PATCH /specialists-info/me`                                                                |
| Категорії           | `GET /consultation-categories/active`                                                                                                                   |
| Консультації        | `GET /specialist-consultations/my`, `POST /specialist-consultations`, `GET/PATCH/DELETE /specialist-consultations/:id`                                  |
| Слоти               | `GET /consultation-slots/my?weekStart=YYYY-MM-DD`, `GET /consultation-slots/my/:id`, `POST /consultation-slots`, `PATCH/DELETE /consultation-slots/:id` |
| Бронювання          | `GET /consultation-bookings/specialist/my`, `GET /consultation-bookings/specialist/my/:id`                                                              |
| Файл запиту клієнта | `GET /consultation-bookings/specialist/my/:id/file`                                                                                                     |
| Відгуки             | `GET /consultation-reviews/specialist/:ownSpecialistId`                                                                                                 |
| Приватні зображення | `GET /private-variants/:id`, `GET /private-assets/:mediumAssetId/file`                                                                                  |

В усіх ресурсах використовуються власні `/me`, `/my` або спеціалістські маршрути. Категорії беруться з `/active`: звичайний `GET /consultation-categories` належить менеджерам. Для селекторів власних компаній/консультацій/категорій читаються всі сторінки по 100 записів із підтримкою скасування запиту. Форми не приймають довільний ID власника.

## Бізнес-правила

### Партнер

Компанія створюється чернеткою. Публікація потребує `companyName`, `contactEmail`, `phone`, `logoId`, головного фото, сайту та коротких/повних описів UA/PL/EN/RU. Інтерфейс показує відсутні поля і не пропонує публікацію до їх заповнення. Сервер повторно перевіряє всі умови. `blocked` та `archived` компанії не редагуються. Партнер не має API видалення компанії.

Банер створюється лише для активної власної компанії. Створення та редагування — multipart, з обов’язковим файлом під час створення та необов’язковою заміною під час редагування. Зміни автоматично встановлюють `pending_review`; окрема кнопка надсилання на модерацію не потрібна. `active` і `finished` банери не редагуються, компанія також має бути доступна для змін. Схвалення, відхилення, запуск і завершення кампанії виконує менеджер. Партнер бачить причину відхилення, період і ліміт показів, кількість показів/кліків і CTR. Перегляд банера в кабінеті не збільшує його покази.

### Спеціаліст

Консультація має категорію, 4 назви та 4 описи, тривалість 5–60 хвилин, ціну з двома десятковими знаками і 1–4 мови `UA/PL/EN/RU`. Валюта бронювань бека — PLN. Верифікація спеціаліста і рейтинг доступні лише для перегляду. Архівування консультації використовує DELETE, який у сервері змінює статус; це не фізичне видалення.

Слот можна створити для активної консультації у майбутньому. Тривалість визначає сервер. Перетини заборонено. `held` і `booked` слоти не можна змінювати/скасовувати; UI пропонує ці дії для `open`. Змінювати тривалість консультації за наявності майбутніх слотів забороняє сервер.

`weekStart` — календарна дата Варшави. Поле datetime також означає Варшаву, незалежно від часового поясу браузера. Перед запитом воно перетворюється на ISO UTC. Неіснуючі або неоднозначні години під час переходу на літній/зимовий час відхиляються з поясненням. Календар та список мають серверну пагінацію; календар прямо повідомляє, що відображає поточну сторінку тижня.

Бронювання для спеціаліста доступні лише для читання та скачування файлу. Перенесення, скасування, оплата, підтвердження dev і retry-операції мають guards користувача або менеджера, тому у цьому кабінеті відсутні. Посилання на зустріч показується для готової оплаченої/завершеної зустрічі. Зовнішні URL проходять перевірку HTTP(S). Відгуки спеціаліста — лише опубліковані; модерація менеджерська.

## Дані й компоненти

`resources.ts` — каталог ресурсів, дозволені статуси, поля DTO і колонки. `Editor` додає серверні зв’язки та використовує спільний `Form`. `form-data.ts` серіалізує числа, ID, мовні масиви, списки сертифікатів, соціальні посилання та дати. Поля з backend `MinLength(1)` не очищуються порожнім рядком; при спробі очистити вже встановлене значення показується повідомлення. Текстові поля, які допускають порожнє значення, можуть очищуватись. Паролі не обрізаються через `trim()`.

HTTP-транспорт залишає формування multipart boundary браузеру, використовує `no-store`, bearer header і AbortSignal. Порожній 204 коректно обробляється, неправильний JSON або структура сторінки спричиняють явну помилку. Приватні картинки отримуються з bearer header і відображаються через короткоживучий object URL; токен не потрапляє до URL. Object URL відкликається після використання. HTML із API не вставляється через `dangerouslySetInnerHTML`.

## Межі перевірки

Контрактні тести перевіряють транспорт, сесію, недозволені ролі, серіалізацію й Warsaw DST. Playwright перевіряє взаємодію зі сторінками та перехоплює мережеві запити. Є сценарії обох ролей, прямих URL, створення компанії/банера/консультації/слота, публікації, авторизованого скачування, відновлення, зміни пароля, фільтрів і пагінації, помилок, виходу й групованого меню.

Ці перевірки підтверджують поведінку фронтенду та відповідність прочитаним контрактам, але не працездатність бази, SMTP, S3 або провайдера зустрічей реального середовища. Реальні облікові дані не використовувалися. Сусідні проєкти не змінювалися.

## Спільна архітектура інтерфейсу з менеджерською CRM

Оболонка використовує перенесені `components/layout-components/{app-shell,header,sidebar,page}`. Sidebar має ті самі згортані групи, бренд Residdy Workflow, ширину 246px і нижній статус; Header — 70px, навігаційний шлях, перемикач теми, профіль і вихід. AppShell зберігає фіксовану висоту viewport, власну прокрутку контенту та мінімальну ширину 1080px.

18 спільних SCSS-модулів компонентів, `crm.module.scss` і `dashboard.module.scss` перенесено без змін. Огляд використовує ту саму структуру карток статистики та модулів. Сторінки входу використовують AuthShell, AuthFormInput, AuthFormSubmit, ThemedIcon, справжні SVG-логотипи та ThemeSwitch. Форми використовують TextInput, FormTextarea, FormSelect і FormFooter. Клієнтська валідація та власні API партнерів/спеціалістів збережені.

Розподіл відповідальності: `shared/providers/{Providers,AuthProvider}`, `shared/auth/auth-context`, `shared/hooks/useAuth`, `shared/guards/{AuthGuard,RoleGuard}`, `shared/query/create-query-client`, `shared/theme/{theme,ThemeProvider}`. Публічні й приватні маршрути розділено route groups, як у менеджерському застосунку. Основний простір — `/main`; `/workspace` залишений лише як редирект для сумісності.

У партнерів і спеціалістів DTO профілю не містить менеджерського поля `theme`. Тому та сама візуальна зміна теми зберігається локально через спільний theme store без викликів менеджерського API.
